# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm run dev       # Next.js dev server (Turbopack)
npm run build     # next build (type-checks, prerenders the page)
npm run lint      # eslint .
npm run typecheck # next typegen && tsc --noEmit
npm run lint:fix  # eslint . --fix
npm run check     # typecheck + lint
npm run clean     # remove .next and build caches
npm run start     # next start (run build first)
```

A versioned `.githooks/pre-push` hook (enable with `git config core.hooksPath .githooks`) runs `scripts/update-readme.mjs`, which regenerates the README's marked Scripts and Project structure sections and aborts the push if they changed. `main` is branch-protected on GitHub: push a branch and open a PR.

Branch names must be `<feature|bug|spike|hotfix>/<issue-id>-<summary>` (lowercase, hyphenated, e.g. `feature/12-add-login`) or `release/<major.minor[.patch]>`. Create the GitHub issue first to get the ID. The same pattern is checked by `.github/workflows/branch-name.yml` on PRs, and the `.claude/hooks/check-branch-name.py` hook (wired up in `.claude/settings.json`) blocks Claude from creating or pushing branches that do not match.

There is no test runner configured. Both `package-lock.json` and `pnpm-lock.yaml` are present; no package manager is mandated by the repo.

## State of the project

Next.js App Router site (Next 16, React 19, TypeScript 6, ESLint 10 flat config with `eslint-config-next`). It is not yet an application:

- `src/app/layout.tsx` is the root layout: metadata (title/description from the profile), the Google Fonts link tags, the pre-paint theme script and the `index.css` import. `<html>` has `suppressHydrationWarning` because that script sets `data-theme`. `reactStrictMode` is on in `next.config.ts`. Components using hooks, refs, observers, `localStorage` or event handlers start with `'use client'`; the rest are server components.
- `src/app/page.tsx` composes the single-page personal bio/resume site (see Content below). `isLoggedIn` is a placeholder constant (currently `false`), so the drawer menu, hamburger and navbar dropdown are hidden.
- Theming uses daisyUI's theme controller, with no React state: `components/layout/ThemeToggle.tsx` renders a single `swap` button around a checkbox with class `theme-controller` and `value="beatrix-dark"`; while checked daisyUI applies that theme in pure CSS via `:has()`, unchecked falls back to the default light theme. `beatrix-dark` deliberately has no `prefersdark` flag (otherwise unchecking would fall back to dark on dark-mode OSes). The choice is saved in `localStorage` key `theme` (`beatrix-light`/`beatrix-dark`) and defaults to the OS preference on first visit; the checkbox is server-rendered unchecked and synced to the saved/OS theme in the mount effect (no `window` access during SSR), and an inline script in `src/app/layout.tsx` sets `data-theme` on `<html>` before first paint (no flash) which the component removes on mount. Anything keyed on the light theme (the light-theme font override, `cute-wiggle`) uses `:root:not([data-theme="beatrix-dark"], :has(input.theme-controller[value="beatrix-dark"]:checked))`.
- `src/index.css` holds the Tailwind/daisyUI setup, themes, fonts and global element styles (see Styling), imported by the layout.

There are no routes, API calls, or AI/LLM integration yet, despite the `beatrix.ai` name. Check the code before assuming any architecture exists.

## Component layout

`src/components/` is grouped into `layout/` (app chrome: `Navbar`, `NavbarDropdown`, `DrawerMenu`, `Footer`, `BackToTop`, `ThemeToggle`, `FirebaseInit`), `sections/` (the page sections: `Hero`, `Stats`, `About`, `Experience`, `Skills`, `Education`, `BeyondCode`, `UpcomingProjects`) and `ui/` (shared pieces: `Avatar`, `AchievementCard`, `CopyEmailButton`, `Reveal`, `SectionHeading`). Imports are relative with explicit `.tsx`/`.ts` extensions.

## Styling

Tailwind CSS v4 (via the `@tailwindcss/postcss` plugin in `postcss.config.mjs`) and daisyUI v5. There is no `tailwind.config.js`; configuration lives in CSS. `src/index.css` starts with `@import "tailwindcss";` and `@plugin "daisyui" { themes: false; }`, then defines two custom themes with `@plugin "daisyui/theme"`: `beatrix-light` (default) and `beatrix-dark`. Icons come from `lucide-react`; `.lucide` in `index.css` sets their stroke width. Built-in daisyUI themes are disabled, and component classes (`btn`, `card`, ...) are available everywhere. Load daisyUI with `@plugin`, never `@import` (that breaks the build). The two themes use daisyUI's stock palettes: `beatrix-light` is "pastel" and `beatrix-dark` is a true dark cyberpunk theme (colors from Cyberpunk 2077 branding/UI: neon yellow #FCEE0C text, magenta #FF1493 primary, cyan #03D8F3 secondary, neon purple #B026FF accent on black-navy #00060e surfaces, `color-scheme: dark`, square corners). Both themes' corner radii come from the `--radius-*` tokens. The theme names are kept because `ThemeToggle.tsx` references them. Hover effects use a soft glow. Fonts are loaded from Google Fonts via link tags in `src/app/layout.tsx`: dark theme uses Rajdhani (body, `font-sans`) and Orbitron (headings and buttons, `font-display`, uppercase); the light theme overrides those two variables with Quicksand and Fredoka in normal case, via a `:root:has(input.theme-controller[value="beatrix-light"]:checked)` rule in `index.css`. All `<button>`s are globally styled `btn` (that rule is unlayered and would override daisyUI's layered `btn-primary` text color, so `button.btn-primary/-secondary/-accent` are re-applied after it) (plus `.button-primary/-secondary/-accent` variants) with a neon hover glow, a shine sweep (`shine-sweep` keyframes on `::after`) and a standalone `.hover-neon` class (the same lift, glow and shine as a primary button, for any element such as sidebar links; recolor with `[--hover-color:var(--color-accent)]`; in the light theme the hover text is auto-darkened via `--hover-text` since pastel colors are too pale to read), a quieter `.hover-subtle` (faint tint, primary text, 2px nudge; used in the drawer menu and footer links), and an opt-in glitch (`glitch` keyframes): `.button-glitch` is a separate button style combined with a color class, e.g. `button-secondary button-glitch`, and `.glitch-hover` applies it to any element such as the navbar title; in the light theme both classes play a cute jelly wiggle, `cute-wiggle`, instead) in `src/index.css`; all disabled under `prefers-reduced-motion`. Dependencies were added with pnpm, so `pnpm-lock.yaml` is current.

## Content (bio / resume landing page)

The page is for general recruiters: the site owner, an Engineering Manager (Android & AI/ML), tone "professional with a wink, leaning cyberpunk". **All copy, labels, metrics and links live in `src/data/profile.json`** (private, git-ignored; `profile.example.json` is the committed placeholder fallback), loaded at runtime by `src/lib/profile-store.ts` (see Deployment) and typed by `src/data/profile.ts` (the `Profile` interface; update both together when adding fields). The root layout fetches it per request (`force-dynamic`) and `ProfileProvider` hands it to components, which read it with `useProfile()` (so they are client components). Components and `main.tsx` (page title) contain no hardcoded text, so content can be regenerated or edited by changing only the JSON (that includes the sign-in overlay (`upcomingProjects.lock`), `upcomingProjects.unlockedLabel` and the drawer headings and admin link in `nav`; `getProfile()` fills any key missing from the stored file from `profile.example.json`, so add new fields to the example too) (metrics come from the resume, never invent numbers). Sections, in order, are `Hero` (text-rotate, aura + hover-3d `Avatar`, CTA buttons, copy-email toast), `Stats` (daisyUI stats with a JS count-up; daisyUI's countdown was dropped because it clips digits in fonts with uneven digit widths), `About` (chat bubbles), `Experience` (a grid of draggable daisyUI `diff` before/after cards from `experience.achievements`, then a timeline with collapse accordions; each card must be a true before/after pair from the resume; `AchievementCard` lists the item's `pains` while the red (before) side covers most of the card and its `solutions` while the green (after) side does, by watching the `.diff-resizer` size with a ResizeObserver since daisyUI's diff has no events; the pain points are inferred from each card's "before" state in the resume, so review them), `Skills` (tabs), `Education`, `BeyondCode` (hover-3d cards, skeleton/loading), then `Footer` and `BackToTop` (a fixed bottom-center button that springs in only within 120px of the page bottom, wibbles periodically (`wibble` keyframes, paused on hover) and smooth-scrolls to the top). Its styles are the `.back-to-top` rules in `index.css`, driven by a `data-visible` attribute, because unlayered `.button-*` rules override Tailwind position/transition utilities; the footer has extra bottom padding so the button does not cover text. `.button-*` + `fixed`/`absolute` is also re-applied in `index.css`. `Reveal` + `hooks/useInView.ts` handle scroll-in animation (the IntersectionObserver only fires on real scrolling in some headless browsers). No proficiency ratings are shown on purpose. The phone number is intentionally not published.

Files in `public/`: `Abhirup_Ghosh_Resume.docx` (private, git-ignored; the example profile points at `/resume.docx`) is a copy of the resume with the phone number removed, used by the download buttons (swap in a PDF and update `person.resumeFile` in `profile.json`); `avatar.jpg` (not yet added) is the photo, and `Avatar.tsx` falls back to initials until it exists. Text contrast was audited in both themes (all visible text >= 4.5:1, 3:1 for large text; the light theme's secondary/accent/error/success `-content` colors and `neutral` are deliberately darker than daisyUI's stock pastel for this reason, so re-audit if you change them). Use `text-brand`, `text-brand-2`, `text-brand-3` (not `text-primary`/`secondary`/`accent`) for text and icons, since the pastel light theme's colors are too pale to read as text. lucide-react has no GitHub/LinkedIn brand icons, so `CodeXml`/`Users` stand in. daisyUI's `tabs` need the radio `input.tab` and `.tab-content` as direct children of `.tabs` (no wrapper elements). The selected skills tab is highlighted by a darker pill (dark purple with light text in the light theme, pink in the dark theme) that slides to the clicked tab: `Skills.tsx` measures the checked radio and sets `--pill-x/y/w/h` on `.tabs`, and `index.css` transitions them (enabled via `data-ready` after first placement, re-measured on resize and font load). The panel itself is not animated.

## Responsive layout

Mobile-first, checked from 320px to 1920px in both themes. `app/page.tsx` owns `isLoggedIn` (placeholder) and passes it to `Navbar`. The drawer is never permanent: at every width it is hidden until the navbar's menu button opens it as a slide-over (`w-72`/`sm:w-80`, `max-w-[85vw]`), and both only exist when logged in. Page content fills the available width up to `max-w-screen-2xl`, centered, with padding that grows at `sm`/`lg`. The navbar is a fixed top bar: `app/page.tsx` wraps it in a full-width `<header className="sticky top-0 z-30 ...">` (semi-transparent with backdrop blur and a bottom border) placed directly inside `drawer-content`, with the capped content container inside the header; keep it outside the page content container so sticky lasts the whole page. The navbar's left half is `flex-1 min-w-0` with a truncating title that shrinks on phones, and the right half is `flex-none`. Because unlayered `.button-*` rules beat daisyUI's layered modifiers, `index.css` re-applies `btn-square` and keeps `swap` buttons as a grid for `.button-*`; use `btn-square` with `.button-*` for icon buttons, and `self-start`/`self-center` rather than width utilities for button width.

## Deployment (Firebase App Hosting)

`apphosting.yaml` configures Firebase App Hosting (`minInstances: 0`, `maxInstances: 2`) and names two secrets, never their values: `PROFILE_JSON_URL` (runtime) and `EXAMPLE_API_KEY` (runtime). Create them with `firebase apphosting:secrets:set <NAME>`. `PROFILE_JSON_URL` is available at runtime: `src/lib/profile-store.ts` reads the `gs://bucket/object` JSON through the Storage REST API as the App Hosting service account (metadata-server token; `roles/storage.objectUser` on the bucket, since the admin panel writes it back) and caches it ~30s per instance, so edits go live within ~30s with no rebuild. Without `PROFILE_JSON_URL` (local dev) it reads `src/data/profile.json` (git-ignored), falling back to `profile.example.json`; for local GCS runs set `GOOGLE_OAUTH_ACCESS_TOKEN=$(gcloud auth print-access-token)`. The admin panel (`/admin`, `src/app/api/admin/cms/route.ts`) saves `profile.json` straight to that object (only that file when GCS is configured). Its API requires a Firebase ID token (`src/lib/admin-auth.ts`) whose verified email has `admin: true` on its `allowed_emails/{email}` Firestore doc; it needs `NEXT_PUBLIC_FIREBASE_API_KEY` and `NEXT_PUBLIC_FIREBASE_PROJECT_ID` on the server. The check is skipped outside production (the dev server is local). Secrets used by API routes (see `src/app/api/example/route.ts`) are read server-side only, with no `NEXT_PUBLIC_` prefix, and must never be returned in responses. Firebase Analytics and App Config (Remote Config) are configured via `src/lib/firebase.ts` and loaded via `<FirebaseInit />` using public `NEXT_PUBLIC_FIREBASE_*` variables. The resume `.docx` is git-ignored, so host it elsewhere (e.g. Cloud Storage) and point `person.resumeFile` at the URL. The user runs `firebase login` and the console GitHub connection themselves.

## Tooling constraints worth knowing

- A single `tsconfig.json` (Next's, covering `src/`) enables `noUnusedLocals`/`noUnusedParameters`, so unused imports fail `npm run build`.
- `verbatimModuleSyntax` is on: use `import type` for type-only imports.
- `erasableSyntaxOnly` is on: no `enum`, `namespace`, or constructor parameter properties.
- `allowImportingTsExtensions` is on, and existing code imports with explicit extensions (`../components/Hero.tsx`).
- ESLint uses flat `eslint-config-next` (`core-web-vitals` + `typescript`, which include `react-hooks`) in `eslint.config.mjs`.
- There is no build-time profile alias or `prebuild` step any more; do not import `profile.json` directly. Server code uses `getProfile()` from `src/lib/profile-store.ts`, client components use `useProfile()`.
- The ESLint config is not type-aware (`recommended`, not `recommendedTypeChecked`).
