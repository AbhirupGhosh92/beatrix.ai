This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

A versioned `.githooks/pre-push` hook (enable with `git config core.hooksPath .githooks`) runs `scripts/update-readme.mjs`, which regenerates the README's marked Scripts and Project structure sections and aborts the push if they changed. `main` is branch-protected on GitHub: push a branch and open a PR.

Components must be functional (hooks only; no class components), and every GitHub issue and PR must use the standard detailed format; see `.claude/rules/react.md`, `.claude/rules/github-workflow.md` and `.claude/rules/openspec.md` (templates in `.github/`). All AI agents working in this repo must follow them.

From version 1.2.0 the workflow is spec-driven with OpenSpec: current behavior lives in `openspec/specs/<capability>/spec.md` and each non-trivial change is a folder `openspec/changes/<name>/` (proposal, design, tasks, spec deltas) created with `/opsx:propose`, implemented with `/opsx:apply` and archived with `/opsx:archive` before the PR is ready. The issue comes first, then the branch, then the change; exemptions, the issue/branch/PR mapping and spec-writing rules are in `.claude/rules/openspec.md`. Keep `openspec/specs/` accurate (`openspec validate --all`), and never invent behavior in a spec.

Branch names must be `<feature|bug|spike|hotfix>/<issue-id>-<summary>` (lowercase, hyphenated, e.g. `feature/12-add-login`) or `release/<major.minor[.patch]>`. Create the GitHub issue first to get the ID. The same pattern is checked by `.github/workflows/branch-name.yml` on PRs, and the `.claude/hooks/check-branch-name.py` hook (wired up in `.claude/settings.json`) blocks Claude from creating or pushing branches that do not match.

There is no test runner configured. Both `package-lock.json` and `pnpm-lock.yaml` are present; no package manager is mandated by the repo.

## State of the project

Next.js App Router site (Next 16, React 19, TypeScript 6, ESLint 10 flat config with `eslint-config-next`). It is not yet an application:

- `src/app/layout.tsx` is the root layout: metadata (title/description from the profile), the Google Fonts link tags, the pre-paint theme script and the `src/index.css` import. `<html>` has `suppressHydrationWarning` because that script sets `data-theme`. `reactStrictMode` is on in `next.config.ts`. Components using hooks, refs, observers, `localStorage` or event handlers start with `'use client'`; the rest are server components.
- `src/app/page.tsx` composes the single-page personal bio/resume site (see Content below). Login state and role come from the server session (`GET /api/auth/me`, 401 when anonymous), not from Firebase client state: the drawer, hamburger and navbar dropdown show only when a session exists, and the drawer's admin link only for roles holding `cms:write`. The drawer's menu entries are `nav.drawerItems` objects (`id`, `label`, `href`, `icon`, `enabled`) in the profile; `DrawerMenu` shows an entry only when `enabled` is true and the role holds the permission `requiredPermission(href)` returns, and `getProfile()` reads legacy string entries (or any entry without `enabled: true`) as disabled. `src/lib/drawer.ts` (`visibleDrawerItems`, `hasDrawerContent`) is the one place that decides what the drawer lists; when it would list nothing (no usable entry and no `cms:write` admin link) the page renders neither the menu button (`Navbar` `showMenu`) nor the drawer, while the top bar with the brand, theme toggle and sign-in stays.
- Theming uses daisyUI's theme controller, with no React state: `components/layout/ThemeToggle.tsx` renders a single `swap` button around a checkbox with class `theme-controller` and `value="beatrix-dark"`; while checked daisyUI applies that theme in pure CSS via `:has()`, unchecked falls back to the default light theme. `beatrix-dark` deliberately has no `prefersdark` flag (otherwise unchecking would fall back to dark on dark-mode OSes). The choice is saved in `localStorage` key `theme` (`beatrix-light`/`beatrix-dark`) and defaults to the OS preference on first visit; the checkbox is server-rendered unchecked and synced to the saved/OS theme in the mount effect (no `window` access during SSR), and an inline script in `src/app/layout.tsx` sets `data-theme` on `<html>` before first paint (no flash) which the component removes on mount. Anything keyed on the light theme (the light-theme font override, `cute-wiggle`) uses `:root:not([data-theme="beatrix-dark"], :has(input.theme-controller[value="beatrix-dark"]:checked))`.
- `src/index.css` only imports Tailwind and the style files in `src/styles/` (see Styling and Style files), and is imported by the layout.

There are no routes, API calls, or AI/LLM integration yet, despite the `beatrix.ai` name. Check the code before assuming any architecture exists.

Dependencies were added with pnpm, so `pnpm-lock.yaml` is current.

The page is for general recruiters: the site owner, an Engineering Manager (Android & AI/ML), tone "professional with a wink, leaning cyberpunk". **All copy, labels, metrics and links live in `src/data/profile.json`** (private, git-ignored; `profile.example.json` is the committed placeholder fallback), loaded at runtime from Firebase Storage by `src/lib/profile-store.ts` through `src/middleware/profileService.ts` and the private `getProfile` Cloud Function (see Deployment) and typed by `src/data/profile.ts` (the `Profile` interface; update both together when adding fields). The root layout fetches it per request (`force-dynamic`) and `ProfileProvider` hands it to components, which read it with `useProfile()` (so they are client components). Components and `main.tsx` (page title) contain no hardcoded text, so content can be regenerated or edited by changing only the JSON (that includes the sign-in overlay (`upcomingProjects.lock`), `upcomingProjects.unlockedLabel` and the drawer headings and admin link in `nav`; `getProfile()` fills any key missing from the stored file from `profile.example.json`, so add new fields to the example too) (metrics come from the resume, never invent numbers). Sections, in order, are `Hero` (text-rotate, aura + hover-3d `Avatar`, CTA buttons, copy-email toast), `Stats` (daisyUI stats with a JS count-up; daisyUI's countdown was dropped because it clips digits in fonts with uneven digit widths), `About` (chat bubbles), `Experience` (a grid of draggable daisyUI `diff` before/after cards from `experience.achievements`, then a timeline with collapse accordions; each card must be a true before/after pair from the resume; `AchievementCard` lists the item's `pains` while the red (before) side covers most of the card and its `solutions` while the green (after) side does, by watching the `.diff-resizer` size with a ResizeObserver since daisyUI's diff has no events; the pain points are inferred from each card's "before" state in the resume, so review them), `Skills` (tabs), `Education`, `BeyondCode` (hover-3d cards, skeleton/loading), then `Footer` and `BackToTop` (a fixed bottom-center button that springs in only within 120px of the page bottom, wibbles periodically (`wibble` keyframes, paused on hover) and smooth-scrolls to the top). Its styles are the `.back-to-top` rules in `src/styles/components/back-to-top.css`, driven by a `data-visible` attribute, because unlayered `.button-*` rules override Tailwind position/transition utilities; the footer has extra bottom padding so the button does not cover text. `.button-*` + `fixed`/`absolute` is also re-applied in `src/styles/components/buttons.css`. `Reveal` + `hooks/useInView.ts` handle scroll-in animation (the IntersectionObserver only fires on real scrolling in some headless browsers). No proficiency ratings are shown on purpose. The phone number is intentionally not published.

Text contrast was audited in both themes (all visible text >= 4.5:1, 3:1 for large text; the light theme's secondary/accent/error/success `-content` colors and `neutral` are deliberately darker than daisyUI's stock pastel for this reason, so re-audit if you change them). ## Style files

Styles live in `src/styles/`, grouped by concern; `src/index.css` imports them in a fixed order that preserves the original cascade (all rules are still unlayered, so file order matters; do not reorder the imports). `tokens/themes.css` (daisyUI plugin and the two themes), `tokens/variants.css` (the `theme-light` variant), `tokens/code.css` (the code palette), `tokens/fonts.css` (`@theme` fonts, light-theme font override), `base/elements.css` (`body`, headings, `button`, `.lucide`, smooth scroll), `components/` (`buttons.css`, `google-signin.css`, `navigation.css` for the dropdown animation, `text-colors.css` for `text-brand*` and `text-pain/gain`, `surfaces.css`, `typography.css`, `back-to-top.css`, `skills-tabs.css`) and `effects/` (`hover.css`, `reveal.css`, `glitch.css`, `reduced-motion.css`) and `vendor/` (`json-view.css`, `monaco.ts`). Add a new rule to the file for its concern, or a new file plus an `@import` in `src/index.css`. This is part of the OpenSpec change `organise-styles` (issue #69).

**Semantic classes.** Visual identity (colors, surfaces, typography, borders, effects) comes from named classes in `src/styles/`, not repeated utility lists; structural utilities (`flex`, `grid`, `gap-*`, spacing, responsive layout) stay inline in the JSX. Current set: `surface` (`bg-base-200 border border-base-300`), `edge-b` (bottom divider), `text-muted` (`text-base-content/60`), `text-meta` / `text-meta-strong` (`text-sm` at 70% / 80% opacity), `heading-display` (`font-display uppercase tracking-wide`, normal case in the light theme via the list in `tokens/fonts.css`), plus the existing `text-brand*`, `text-pain/gain`, `button-*`, `hover-*` and `glitch-hover`. The `surface`, `edge-b`, `text-*` and `heading-display` classes are in `@layer components`, so a Tailwind utility on the same element can still adjust them. Add a class only for an exact repeat (at least three uses) that expresses identity, and use theme tokens, never raw colors. Gotchas: a component that sets its own background keeps explicit utilities (`modal-box surface` renders a different background because daisyUI's modal rule wins); write light-theme overrides with `@variant theme-light { ... }` (defined in `tokens/variants.css`) instead of repeating the long selector; and when you add a semantic class that changes text case, add it to the light-theme `text-transform` list in `tokens/fonts.css`.

**Layering status.** The global `button` rule, the `.button-*` rules and their re-apply workarounds (`button.btn-*`, `btn-square`, `fixed`, `absolute`, `swap`) are deliberately still unlayered: moving them into `@layer base` made every button variant lose its background and border (17 to 49 computed properties changed per variant), so do not layer or remove them without re-testing every button class combination in both themes. The other style files are unlayered too, so file order in `src/index.css` matters. 

**Vendor adapters.** Third-party UI takes its colors from a shared code palette: the `--code-*` tokens in `tokens/code.css` (light on `:root`, dark on `[data-theme="beatrix-dark"]` / the dark toggle), whose values equal the colors those themes used before. The JSON tree viewer is mapped in `vendor/json-view.css` (its `--w-rjv-*` variables on `.w-json-view-container`), so it follows the tokens immediately. Monaco only accepts concrete colors, so `vendor/monaco.ts` reads the tokens from a hidden `data-theme` probe element (both palettes, whichever theme is active), converts them to hex and defines the two Monaco themes; `JsonEditor.tsx` calls `defineMonacoThemes` before mount and again when the theme flips. To adapt a new library: add the colors it needs as `--code-*` (or new) tokens for both themes in `tokens/code.css`, then add `vendor/<library>.css` mapping the library's CSS variables or class names to those tokens, or `vendor/<library>.ts` when the library needs concrete colors (read tokens with a probe as in `monaco.ts`), and `@import` it last in `src/index.css`. Keep token values plain CSS colors where a `.ts` adapter reads them. Lightning CSS rewrites the dark token selector into `:is(...)`, which takes the strongest branch's specificity, so an override of a dark `--code-*` value must be authored in the same pipeline (a CSS file) or use `!important`. After adding files while the dev server runs, restart it and clear `.next` if Turbopack reports `Can't resolve './styles/...'`.

## Access control (sessions and roles)

Server-enforced, default-deny (OpenSpec capability `access-control`). After Google sign-in the browser posts its ID token to `POST /api/auth/session`, which has the private `sessionCreate` function check the allow list and mint a Firebase session cookie (`__session`, `httpOnly`, `SameSite=Lax`, `Secure` in production, 5 days); `DELETE` clears it. `src/proxy.ts` (Next 16's middleware file; unrelated to the `src/middleware/` services folder) runs on every request, asks `sessionVerify` about the cookie (which also checks revocation and re-reads the role, so role changes and `allowed: false` apply on the next request) and applies `src/lib/access.ts`: public paths are only `/`, `/api/auth/session`, `/_next/*` and public files; any other path needs a session, and `/admin` and `/api/admin/*` need `cms:write`. Page denials redirect to `/`, API denials return 401/403; if the session check is unreachable the gate fails closed. `src/lib/access.ts` is the single policy (roles `reader < user-base < user-advanced < admin`, permissions `site:view`, `features:basic`, `features:advanced`, `cms:write`, `can(role, permission)`, `requiredPermission(path)`, `resolveRole(entry)`); `functions/src/policy.ts` mirrors the roles and `resolveRole` for the functions, so edit both together. A verified email with no `allowed_emails/{email}` entry is registered as a `reader` inside `sessionCreate` (`registerIfAbsent` in `functions/src/users.ts`: create-only, an existing entry only gets `lastLoginAt`), so a first sign-in succeeds; `allowed: false` stays refused. Admins manage users at `/admin/access` through `adminListUsers`/`adminSetUser` (add, setRole, revoke, restore; both need `cms:write`), which refuse self-revoke, self-demote and removing the last active admin; the panel writes only `role`/`allowed`. Terraform only seeds `allowed_admin_emails` docs. The role is `allowed_emails/{email}.role`; no role is `reader`, a legacy `admin: true` entry without a role is `admin`, an unknown value is `reader`, `allowed: false` or a missing entry is no access. A route tied to a menu item is listed in `FEATURE_ROUTES` in `access.ts`; `src/proxy.ts` answers 404 (page rewrite or API JSON) for every role while that item is not enabled in the profile, after the permission check, and an unreadable profile keeps it closed (the flag can only close a route, never grant access). To add a route's permission, add it to `ROUTE_PERMISSIONS` in `access.ts` (unlisted routes already need `site:view`); never add a route to the public lists without a reason. The UI hides controls with `can()`, but the server decides.

## Resume builder config and validation

The resume builder (OpenSpec change `resume-builder`, issue #75) has its own config, separate from the landing page profile: `cms/resume-config.json` in Storage, typed by `src/data/resumeConfig.ts`, with `src/data/resume-config.example.json` as the fallback for any missing key. Server code reads it with `getResumeConfig()` from `src/middleware/resumeConfigService.ts` (private `getResumeConfig` function, cached ~30s); `sanitizeResumeConfig` in `src/lib/resumeConfigSanitize.ts` replaces invalid limits, rules or default structure with the example's and drops invalid templates, so a CMS typo never breaks the builder. A template is style tokens from a closed vocabulary plus a layout id implemented in code. An admin creates the file through the CMS "new file" flow (paste the example). `src/lib/resumeValidation.ts` (structure and data checks) is mirrored byte-for-byte in `functions/src/resumeValidation.ts` because `functions/` is a separate package; edit both together (`diff` must be empty).

**Resume builder (storage, API, page).** `/resume-builder` (components in `src/components/resume/`) lists the signed-in user's resumes and edits one with a structure-driven form: base users save explicitly and use the default structure, roles with `features:advanced` autosave, edit the structure and have no cap. The browser calls only `/api/resumes`, `/api/resumes/[id]` and `/api/resumes/config`; the handlers (each also checks the `resume-builder` menu flag with `featureOff`) go through `src/middleware/resumeService.ts`, which forwards the `__session` cookie plus the resume config's limits and rules to the private `resumeList`/`resumeGet`/`resumeCreate`/`resumeSave`/`resumeDelete` functions (`functions/src/resumes.ts`). The functions verify the cookie themselves (`requireSession`), so the owner is always the verified email and another user's id is a 404. Resumes are `owners/<sha256(email)>/<id>.json` in the separate bucket `<project id>-resumes` (30-day noncurrent retention); `resume_owners/{email}` in Firestore holds the count and size used for the cap (reserved in a transaction before the object is written) and for the later admin cleanup. A save quotes the object's Storage generation, and a mismatch is a 409. Revoking a user keeps their resumes; `/admin/access` lists owners without access (`OrphanedResumes`, `/api/admin/resumes`, functions `adminListResumeOwners` / `adminPurgeResumeOwner`: email, count, size and time only, never content) and an admin can hard delete one owner's data after typing the email (every version, refused while the owner still has access, logged in `resume_audit`); these routes are not flag-gated. Drafts always save within the size and shape limits; full validation only gates Generate. Export runs entirely in the browser (`src/lib/resume/`): `model.ts` turns structure + data into a format-independent document (header from the first non-repeatable section, entries from repeatable sections, blank values dropped), and `markdown.ts`, `toDocx.ts` (`docx`, real Title/Heading styles, bullet lists, tab-stopped dates, Word-default fonts, one column for every layout so it converts cleanly to PDF) and `toPdf.ts` (`@react-pdf/renderer`, PDF standard fonts, `classic` and `sidebar` layouts) render it. `export.ts` imports the DOCX and PDF renderers dynamically on Generate (they are separate chunks, not loaded by any page), produces exactly one file per click and warns about characters the PDF standard fonts cannot draw. A template is the config's style tokens (`font`, `baseSize`, `accent`, `spacing`) plus a layout id; there is no watermark. Picking a template for PDF or DOCX shows a preview (`TemplatePreview`): the real PDF renderer fed `sampleData(structure)` (`src/lib/resume/sample.ts`, built from the structure's placeholders so custom structures work, never the user's resume), in an inline frame, or an "open preview" link when `navigator.pdfViewerEnabled` is false; the PDF library loads when the preview appears.

## Responsive layout

Mobile-first, checked from 320px to 1920px in both themes. `app/page.tsx` owns `isLoggedIn` (placeholder) and passes it to `Navbar`. The drawer is never permanent: at every width it is hidden until the navbar's menu button opens it as a slide-over (`w-72`/`sm:w-80`, `max-w-[85vw]`), and both only exist when logged in. Page content fills the available width up to `max-w-screen-2xl`, centered, with padding that grows at `sm`/`lg`. The navbar is a fixed top bar: `app/page.tsx` wraps it in a full-width `<header className="sticky top-0 z-30 ...">` (semi-transparent with backdrop blur and a bottom border) placed directly inside `drawer-content`, with the capped content container inside the header; keep it outside the page content container so sticky lasts the whole page. The navbar's left half is `flex-1 min-w-0` with a truncating title that shrinks on phones, and the right half is `flex-none`. Because unlayered `.button-*` rules beat daisyUI's layered modifiers, `src/styles/components/buttons.css` re-applies `btn-square` and keeps `swap` buttons as a grid for `.button-*`; use `btn-square` with `.button-*` for icon buttons, and `self-start`/`self-center` rather than width utilities for button width.

## Deployment (Firebase App Hosting)

`apphosting.yaml` configures Firebase App Hosting (`minInstances: 0`, `maxInstances: 1`) and currently declares no secrets. **Architecture: browser → Next.js server (`src/middleware/` + `src/app/api/`) → private Cloud Functions → Firebase Storage/Firestore.** The browser never talks to a Cloud Function; only the Next.js server does, so function URLs, tokens, paths and payloads stay server-side. `src/middleware/` holds server-only services (`import 'server-only'`, so client imports fail the build; do not add an `index.ts` or a `middleware.ts` there that Next could mistake for its own middleware file): `cloudFunctions.ts` (`callCloudFunction`, authenticates every call with a Google ID token for the App Hosting service account via google-auth-library, reusing each token ~50 minutes), `sessionService.ts` (`createSession`/`verifySession` over the `sessionCreate`/`sessionVerify` functions and the `__session` cookie options), `profileService.ts` (`getProfile()` for the root layout, cached ~30s, falling back to `src/data/profile.json` in dev and then `profile.example.json`) `adminService.ts` (list/get/save CMS files) and `userService.ts` (list and update users). `src/app/api/admin/cms/route.ts` and `src/app/api/admin/users/route.ts` are thin handlers over those services (shared helpers in `routeHelpers.ts`); `/admin` calls them with `Authorization: Bearer <Firebase ID token>`, which the routes forward to the functions. `/admin` has a top navbar (`components/layout/AdminNav.tsx`, from `app/admin/layout.tsx`) with **CMS** (`/admin/cms`, the JSON editor) and **Access** (`/admin/access`, the users table with role select and revoke/restore); `/admin` redirects to `/admin/cms`. The backend lives in `functions/` (separate pnpm package with its own `pnpm-workspace.yaml`, Node 22, `firebase-admin` + `firebase-functions` v2): every API is its own plain-HTTP function (`getProfile`, `adminListFiles`, `adminGetFile`, `adminSaveFile`, `adminListUsers`, `adminSetUser`, `sessionCreate`, `sessionVerify`, `status`; POST JSON, not `onCall`, because callable auth would clash with the IAM token) created with `privateEndpoint()` in `functions/src/http.ts`, whose invoker is only `firebase-app-hosting-compute@<project>.iam.gserviceaccount.com`, so Cloud Run IAM rejects everyone else. The admin functions additionally verify the forwarded Firebase ID token and require the verified email's `allowed_emails/{email}` entry to resolve to a role holding `cms:write` (`requirePermission` in `functions/src/auth.ts`). Profile and CMS JSON live under `cms/` in the default Storage bucket (`cms-backups/` keeps the previous version on every save); `storage.rules` denies all client access. Server env: the project id (`NEXT_PUBLIC_FIREBASE_PROJECT_ID`, or App Hosting's `GOOGLE_CLOUD_PROJECT`); for local dev set `FUNCTIONS_CALLER_SERVICE_ACCOUNT=firebase-app-hosting-compute@<project>.iam.gserviceaccount.com` (Terraform's `developer_members` get Service Account Token Creator on it) so the dev server can mint the ID token. Firebase Analytics and App Config (Remote Config) are configured via `src/lib/firebase.ts` and loaded via `<FirebaseInit />` using public `NEXT_PUBLIC_FIREBASE_*` variables; on App Hosting `next.config.ts` fills them from `FIREBASE_WEBAPP_CONFIG`, so there are no per-environment files. The resume `.docx` is git-ignored, so host it elsewhere (e.g. Cloud Storage) and point `person.resumeFile` at the URL.

**Environments (runbook: `terraform/README.md`, skill `provision-environment`, rule `.claude/rules/environments.md`):** `dev`, `staging` and `prod` are separate GCP projects built by the same Terraform (`terraform/environments/<env>.tfvars`, state in `gs://<project>-tfstate`), including the App Hosting backend `beatrix-web` (no GitHub connection; deployed from source via the `apphosting` entry in `firebase.json`), its `firebase-app-hosting-compute` account, the `allowed_emails` admin docs and a keyless GitHub deployer (Workload Identity Federation, limited to the GitHub environment of the same name). `.github/workflows/deploy.yml` deploys dev then staging on every push to `main` and prod only by manual `workflow_dispatch` (release ref + typed `prod` confirmation + `prod-release` reviewer approval); each run (`deploy-environment.yml`) is verify → `terraform plan` + plan guard (`scripts/deploy/plan_guard.py` blocks delete/replace of Firestore, Storage, the App Hosting backend, service accounts, ...) → approve (prod) → CMS snapshot → apply of the SAVED plan → `scripts/deploy-backend.sh --components` for only the components whose source hash changed (`scripts/deploy/components.sh`) → smoke test. Deploys never use `-auto-approve` or `firebase deploy --force` (`infra-check.yml` enforces it) and third-party actions are pinned to commit SHAs. Firestore has delete protection and point-in-time recovery, the CMS bucket is versioned, and `prevent_destroy` guards the stateful resources. Full guide, guarantees and runbooks: `docs/DEPLOYMENT.md`; any change to the pipeline or `terraform/` must keep that document accurate. Create or repair an environment with `./scripts/recreate-environment.sh <env>`: `scripts/env-preflight.sh` stops it with exit code 3 and an `ACTION REQUIRED` list for the steps only the user does (project, billing, Storage "Get started", Google sign-in provider, authorized domain, CLI logins). Agents relay those one at a time, wait for the user, re-run, and never do them or bypass the checks.

## Tooling constraints worth knowing

- A single `tsconfig.json` (Next's, covering `src/`) enables `noUnusedLocals`/`noUnusedParameters`, so unused imports fail `npm run build`.
- `verbatimModuleSyntax` is on: use `import type` for type-only imports.
- `erasableSyntaxOnly` is on: no `enum`, `namespace`, or constructor parameter properties.
- `allowImportingTsExtensions` is on, and existing code imports with explicit extensions (`../components/Hero.tsx`).
- ESLint uses flat `eslint-config-next` (`core-web-vitals` + `typescript`, which include `react-hooks`) in `eslint.config.mjs`.
- There is no build-time profile alias or `prebuild` step any more; do not import `profile.json` directly. Server code uses `getProfile()` from `src/middleware/profileService.ts`, client components use `useProfile()`; `functions/` has its own `package.json`, so install and build it with `pnpm --prefix functions install` / `npm run functions:build`.
- The ESLint config is not type-aware (`recommended`, not `recommendedTypeChecked`).
